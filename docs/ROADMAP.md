# Implementation, adoption and scalability roadmap

VERDANT-X is a working prototype on synthetic data. This document says who would pay for it, how it gets to a first real plant, what has to change for production, and how it scales beyond Turkish cement.

## Part 1. Implementation and adoption strategy

### Who pays, and why

| Who | What they get | Why they pay |
|---|---|---|
| **Exporting plant** (main customer) | Its real emissions, verified and claimable by importers | In 2026, the three synthetic plants pay €52–65 less per tonne of cement on verified data than on default values (€72.58 vs €7.79–20.80, from [CLIMATE_IMPACT.md](CLIMATE_IMPACT.md)). The gap grows as free allocation is phased out to 2034 |
| **EU importer** | A supplier figure it can check itself, and proof the tonnes were not sold to someone else | Lower CBAM bill with less legal risk |
| **Accredited verifier** | Guard flags with reasons, a review queue, and a co-signature that is recorded | Faster reviews; a record of what was signed and when |
| **Regulator / customs** | A public trail of anchored, verified and allocated tonnes | Can spot double claims across importers |

The plant has the strongest reason: on default values each tonne of CO₂ it cuts is worth €0; on verified data it is worth about €77.

### Go-to-market

1. **Industry association.** Start with the Turkish cement association (TürkÇimento), which already argues publicly that actual emissions must be taken into account. One association reaches many exporting plants with similar data.
2. **Verifiers.** Partner with one or two verification bodies accredited for CBAM. They bring plants and gain a faster review tool.
3. **Importers.** Offer the disclosure link to EU importers who buy from pilot plants. Importers need no account; a link is enough.

### Pilot plan

| Phase | Scope | Exit criteria |
|---|---|---|
| **0. Now** | Prototype on Polygon Amoy, synthetic plants | Done: end-to-end flow, 32 backend + 9 contract tests, verified contract source |
| **1. Data pilot** | 1–2 plants, historical months, read-only | Calculation matches the plant's own CBAM figures; guard thresholds re-tuned on real data; false-alarm rate measured |
| **2. Shadow run** | Same plants, live months, one verifier, testnet | Verifier co-signs in VERDANT-X alongside its normal process; importers open disclosure links |
| **3. Production pilot** | Production deployment (see below), first real allocations | Importer uses a VERDANT-X figure in a CBAM declaration |
| **4. Scale** | More plants via the association; more verifiers | Several plants and verifiers on one registry |

### Integration

- **EU CBAM Registry.** VERDANT-X does not replace it. It needs an export of each verified report in the format the Registry and its declarant templates expect, so importers can upload rather than retype. The export is not built yet.
- **Accredited verifiers.** The verifier keeps its own procedure and site visits. VERDANT-X gives it the guard results and records its co-signature. Each verifier is allow-listed on-chain by key fingerprint.
- **Plant systems.** The pilot can start with manual monthly entry (the current form). Later, a connector to the plant's lab and energy systems.

### What production needs

| Need | Today | Production |
|---|---|---|
| Plant data | Synthetic, from published ranges | Real plant data; guard re-tuned on it |
| Emission factors | Official defaults and benchmarks; grid factor and waste-tyre biomass share still marked `verify` | All factors checked against official sources |
| Signing keys | Generated by the server; demo keystore | HSM/KMS per plant and per verifier, held by that party |
| Authentication | None on the API | Per-role login and authorisation |
| Store | In-memory | Persistent database (the `Store` class is the seam) with backups; salts kept as long as reports can be audited |
| Importer check | Hashes, signatures, Merkle proofs in the browser | Also read the contract to confirm the anchored report hash, Merkle root, plant fingerprint and verifier allow-list |
| Chain | Polygon Amoy testnet | Choice of Polygon PoS mainnet or another EVM L2, based on cost, finality and regulator preference |
| Contract admin | One deployer wallet | Multisig owner; validated period format |
| Legal | – | Review of CBAM verification rules, data protection and the role of a verifier's co-signature |

## Part 2. Scalability and sustainability roadmap

### Other CBAM sectors

CBAM already covers iron and steel, aluminium, fertilisers, hydrogen and electricity, and each has the same default-value problem. The code separates the sector from everything else:

| Per sector (new) | Shared (unchanged) |
|---|---|
| `sectors/<sector>.py` implementing `Sector` | Trust layer: canonical JSON, Merkle, hybrid signatures |
| `config/<sector>.yaml`: factors, defaults, benchmarks, thresholds | `VerdantRegistry` contract and chain clients |
| `guard/rules/<sector>.py` and an anomaly feature function | API, disclosure page and browser verification |

Steel and aluminium are the natural next sectors: both have precursors, like clinker in cement, and the pricing module already takes a precursor ratio for the benchmark. See [ARCHITECTURE.md](ARCHITECTURE.md) §8.

### Other exporting countries

The method is set by the EU, not by the exporter, so it carries over. A new country needs its own grid emission factor, its own default values (if the EU publishes country-specific ones) and its carbon price, if any. The deduction for carbon price paid at origin is already in `pricing/cbam_cost.py`; in 2026 Türkiye's is zero.

### Throughput and cost

Only fingerprints go on-chain. Per plant and month: one `anchorReport`, one `coSign`, and one `allocate` per shipment. Measured with `REPORT_GAS=true npx hardhat test`:

| Call | Gas (avg) | How often |
|---|---|---|
| `anchorReport` | 196,496 | once per plant-month |
| `coSign` | 81,924 | once per plant-month |
| `allocate` | 76,001 | once per shipment |
| `registerInstallation` | 93,349 | once per plant |

One plant-month with one shipment uses about **354,000 gas**. The cost in euros depends on the chain and gas price chosen for production; we have not measured it on a mainnet. On-chain storage per report is fixed, whatever the size of the private data. ML-DSA signatures (3,309 B each) stay off-chain.

Off-chain, the work per report is one calculation, seven rules, one model score, one Merkle tree over a few dozen leaves and four signatures. This runs per plant per month, so it is small.

### Future work

- **Zero-knowledge proofs.** Today the importer sees exact disclosed values. A ZK proof could show "intensity below X" or "computed correctly from committed inputs" without revealing the value.
- **On-chain checks in the browser** (see production needs above).
- **CBAM Registry export** and a verifier API.
- **Contract upgrades:** validated period format, verifier assignment per installation, owner actions with a delay.

### Sustainability

- **Energy.** The target chains are proof-of-stake, and the system writes a few transactions per plant per month.
- **Open source.** MIT licence. Verifiers, importers and regulators can read and run the verification code themselves, which is the point of a trust tool.
- **Business model options** (not yet tested with customers):
  - per-report or per-tonne fee to the exporting plant, small next to its CBAM saving;
  - licence for verification bodies (review tooling, many plants);
  - hosted service for an industry association on behalf of its members.
